# Протокол VPS ↔ нода

Нода (`crm-node`, комп Саши) — единственная сторона, которая открывает соединения: сервер никогда не подключается к ней сам.
Все запросы ноды авторизуются заголовком `Authorization: Bearer <NODE_TOKEN>`.
Типы сообщений описаны в `internal/proto/proto.go`.

```
         нода                                     VPS
          │  WS  /api/node/ws  (control, JSON) ─────►│  постоянное соединение, ping каждые 20 с
          │◄──── fetch {sha,size}                    │  «забери новый файл»
          │  GET /api/node/blob/{sha}  (Range) ─────►│  скачивание из буфера, с докачкой
          │──── stored {sha,size} ──────────────────►│  «сохранил и проверил sha256»
          │◄──── serve {id,sha,off,len}              │  «пришли байты для пользователя»
          │  WS  /api/node/stream/{id} ─────────────►│  поток байтов (binary-кадры по 256 КБ)
          │◄──── derive {sha,mime,want}              │  «сделай превью»
          │  WS  /api/node/derived/{sha}/{name} ────►│  загрузка poster.jpg / thumb.jpg / preview.mp4
          │──── probe {sha, duration, w, h, peaks} ─►│  метаданные (и конец обработки)
          │◄──── check {id, shas[]}                  │  сверка после переподключения
          │──── missing {id, shas[]} ───────────────►│
          │◄──── delete {sha}                        │  перенести в trash/ (удалено навсегда в CRM)
          │  GET /api/node/backup ──────────────────►│  снимок базы (VACUUM INTO)
```

## Почему так

- **Управление и данные разведены по разным соединениям.** Control-сокет держит одно долгое соединение с короткими JSON-сообщениями. Под каждую отдачу байтов нода открывает отдельный WebSocket. Поэтому управляющие сообщения не застревают за большими передачами, а противодавление работает средствами TCP: если пользователь поставил видео на паузу, браузер перестаёт читать, VPS перестаёт читать из сокета, и нода блокируется на записи. Дробить данные вручную и вести окна передачи не нужно.
- **WebSocket проходит через любой прокси** (nginx, Caddy, Cloudflare) без буферизации тела, выглядит как обычный HTTPS на 443-м порту и не требует белого IP.
- **Все операции идемпотентны.** Сообщения, отправленные, пока нода была офлайн, теряются, и это нормально: при каждом подключении сервер повторяет сверку `check`, рассылает `fetch` для всех непереданных файлов и `derive` для всех необработанных. Если `fetch` пришёл для файла, который уже есть, нода просто сразу отвечает `stored`.

## Жизненный цикл файла

```
загрузка в браузере ──► uploads/<id>.part (VPS, части по 8 МБ, sha256 считается на лету)
                    ──► blobs/<sha> на VPS, state=buffered (закреплён в буфере)
                    ──► fetch → нода скачивает → проверяет sha256 → fsync → stored
                    ──► state=stored, копия на VPS становится LRU-кэшем
                    ──► derive → нода делает превью → derived/<sha>/… на VPS
просмотр: локальная копия на VPS?  да → отдаём с диска (Range)
                                   нет → serve → нода стримит нужный диапазон
                                   (небольшие файлы после этого кэшируются на VPS)
удаление навсегда (только админ): blob больше нигде не используется → delete → нода кладёт его в trash/
```

Состояния blob в базе: `buffered` (есть только на VPS), `stored` (подтверждён нодой), `missing` (нода не нашла файл при сверке; если файл загрузят заново, состояние восстановится).

## Формат потока данных

Первый кадр — текстовый `StreamHeader {size, off, len, mime?, error?}`. Дальше идут binary-кадры с данными, суммарно ровно `len` байт. Последний кадр — текстовый `StreamEnd {done:true}` или `{error}`.
Для `derived` сервер подтверждает приём нормальным закрытием сокета (status 1000).

## Версии

`proto.Version` передаётся в `hello`. Если версия не совпадает, сервер закрывает соединение и пишет об этом в лог. Сервер и ноду нужно обновлять вместе.
